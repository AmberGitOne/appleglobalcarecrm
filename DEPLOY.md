# Deploying

## Read this first: why not Vercel

Vercel runs serverless functions on a **read-only filesystem**. The only
writable path is `/tmp`, which is wiped between invocations and is not shared
between instances.

This app writes to SQLite on almost every interaction — starring a ticket,
approving leave, releasing a batch. On Vercel those writes would be lost
immediately, and two users could be served different data by different
instances. The app would look like it worked while silently discarding
everything.

So Vercel needs one of these first:

| Option | Code changes |
| --- | --- |
| Host with a persistent disk (Render, Railway, Fly, a VPS) | **none** |
| Vercel + Turso (hosted SQLite / libSQL) | convert ~200 synchronous DB calls across 12 files to async |
| Vercel + Postgres or Neon | the same async conversion, plus SQL dialect changes |
| Vercel, read-only demo | none, but every edit fails |

The rest of this file covers the first option, which runs the app exactly as
it runs locally.

## Render (blueprint included)

`render.yaml` is committed, so Render can provision everything itself.

1. Push this repo to GitHub.
2. Render dashboard → **New** → **Blueprint** → select the repo.
3. Confirm. Render reads `render.yaml` and creates the service plus a 1 GB
   disk mounted at `/var/data`.

The blueprint sets:

- `DB_FILE=/var/data/crm.db` — on the persistent disk, so deploys do not
  reset your data
- `REQUIRE_AUTH=true` — the app is reachable from the internet, so it should
  not be open
- `JWT_SECRET` — generated by Render, never committed

The free plan has **no persistent disk**, so the database would reset on every
restart. The blueprint uses `starter` for that reason.

## Docker (Railway, Fly.io, a VPS, locally)

```bash
docker build -t aglc-crm .
```

```bash
docker run -p 4000:4000 -v aglc-data:/app/data -e REQUIRE_AUTH=true -e JWT_SECRET="$(openssl rand -hex 32)" aglc-crm
```

The `-v` volume is not optional. Without it the database lives inside the
container layer and is destroyed on every restart.

`docker-entrypoint.sh` creates the schema and seeds **only when the database
file is missing**. On later boots it applies pending migrations and leaves
your data alone, so a redeploy never wipes real records.

### Railway

Railway detects the `Dockerfile` automatically. Add a volume mounted at
`/app/data`, then set `REQUIRE_AUTH=true` and a `JWT_SECRET` in the service
variables.

### Fly.io

```bash
fly launch --no-deploy
```

```bash
fly volumes create crm_data --size 1
```

Mount it at `/app/data` in `fly.toml`, then `fly deploy`.

## Before any public deployment

- [ ] `REQUIRE_AUTH=true` — otherwise anyone with the URL has full write access
- [ ] `JWT_SECRET` set to a long random value, never the one in `.env.example`
- [ ] Demo account passwords changed, or those users removed
- [ ] The database is on a **persistent volume**, not the container filesystem
- [ ] `NODE_ENV=production`

Generate a secret with:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

## How auth behaves

With `REQUIRE_AUTH=false` (the local default) the app opens straight into the
CRM, as the prototype did.

With `REQUIRE_AUTH=true`:

- `/api/health` and `/api/auth/login` stay public — everything else returns
  `401` without a valid bearer token
- The browser app shows a sign-in screen, stores the token, and retries
- If the token expires mid-session, the next save prompts for sign-in and then
  retries that save, so the edit is not lost
- Role permissions are enforced server-side: an Agent reading `/api/audit`
  gets `403`, as does an Agent trying to delete a supplier
- Audit rows are attributed to the signed-in user rather than a fallback

## Backing up

The database is a single file. Copy it while the server is running with:

```bash
sqlite3 /var/data/crm.db ".backup '/var/data/backup-$(date +%F).db'"
```

Plain `cp` is not safe on a live database in WAL mode.
